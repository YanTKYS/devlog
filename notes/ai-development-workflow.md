# AI開発体制の検討・運用評価

- 記録日：2026-11-01
- 状態：検討中（現行体制を継続）
- 関連資料：[AIコーディングツール比較（2026年10月）](ai-coding-tools.md)

## 1. 目的

複数のGitHubリポジトリを生成AIエージェントで開発するにあたり、開発品質、利用料金、利用制限、自律実行能力、運用負担を比較し、継続可能な開発体制を検討する。

本資料は製品の一般的な性能比較ではなく、実際の開発運用に基づく判断とその経緯を記録する。

製品の機能や料金は変更されるため、公式情報と実際に確認できた結果を区別する。

## 2. 現在の開発体制

### 役割分担

| 役割 | 担当 |
| --- | --- |
| 設計・要件整理・Issue作成 | ChatGPT |
| 大規模・高難度開発 | Claude Opus 5.5 |
| 小規模・通常開発 | Codex（GPT-6.1 SOL） |
| PRレビュー・修正指摘 | ChatGPT |
| マージ・最終判断 | 利用者 |

`pdfengine` のような高難度開発はClaude Opus、その他の開発は原則Codexが担当する。

### GitHubを介した標準ワークフロー

2026年10月以降、次の方式に統一した。

1. ChatGPTがGitHub Issueを作成し、作業内容を指示する。
2. 開発エージェントがIssueを参照して実装・テスト・コミットを行い、PRを作成する。マージはしない。
3. ChatGPTがPRをレビューし、修正指摘をPRにコメントする。
4. 開発エージェントが指摘を確認し、同じPRへ追加コミットする。
5. ChatGPTが再レビューし、利用者がマージを判断する。

この方式により、指示とレビューの履歴をGitHub上に残し、チャット間でプロンプトを受け渡す手間を削減している。

## 3. 体制見直しの背景

### ChatGPTとCodexの利用枠共通化

OpenAIは2026年12月から、ChatGPT Plus・Pro・BusinessのChatGPTとCodexの利用枠を共通化する方針を発表した。

共通枠はトークン単位で計測され、通常のInstantチャットは消費対象外とされる。

ただし、新しい利用上限や実際の消費量は現時点で十分に把握できない。

現在はChatGPTを設計・レビュー、Codexを実装に利用しているため、小規模開発で大量のトークンを消費すると、設計やレビューに必要な利用枠が圧迫される懸念がある。

このため、小規模開発を別のエージェントに委任する選択肢を検討する。

**共通枠の影響は未確定であり、現時点でCodexを置き換えると決定したわけではない。**

公式情報：[Understanding ChatGPT and Codex usage limits](https://help.openai.com/en/articles/20001625-understanding-chatgpt-and-codex-usage-limits)

## 4. 代替エージェントの評価基準

最重要条件は、**Issueを渡してからPR作成まで、利用者が繰り返し介入せずに作業を任せられること**である。

| 評価項目 | 確認内容 |
| --- | --- |
| 実装品質 | 要件を満たし、既存機能を破壊しないか |
| 自律実行 | IssueからPRまで完遂できるか |
| レビュー対応 | PRコメントを理解し、同じPRで修正できるか |
| 人間の介入回数 | 承認や再指示がどの程度必要か |
| 作業速度 | 着手からPR作成までに要する時間 |
| 並列処理 | 複数リポジトリを同時に開発できるか |
| 利用制限・費用 | 月額料金、実行枠、追加課金の有無 |
| 運用負担 | 環境構築、認証、起動操作、障害対応の手間 |

特に人間の介入回数は、実装品質と同等に重視する。

無料または低価格であっても、頻繁に操作を要求される場合、クラウドエージェントとしての導入効果は低い。

また、所要時間は単純な経過時間だけでなく、利用者の着手待ち、エージェントの実行時間、テスト時間、承認待ちを可能な範囲で分けて記録する。

## 5. 候補サービスの検討

### 比較状況（2026-11-01）

| 候補 | 実行方式 | 状況・評価 |
| --- | --- | --- |
| Codex GPT-6.1 SOL | 公式クラウドエージェント | 現行担当。実績あり |
| Meta Muse | 自身のクラウドVM | 実証済み。品質は良好、承認負担が大きい |
| Muse＋Google Antigravity | MuseのVMから別エージェントを実行 | 個人契約の利用条件上、採用保留 |
| Muse＋Cursor | MuseのVMから別エージェントを実行 | 構成が複雑。未検証 |
| Qwen Code / Qwen系エージェント | CLI、外部実行環境など | 無料クラウド運用の条件・能力が未確認 |
| OpenCode Go | CLI＋GitHub Actions | 有力候補。未検証 |
| Command Code GOAT | 公式Cloud機能（ベータ） | 有力候補。未検証 |

### 5.1 Meta Muse

Metaが提供するパーソナルAIエージェント。自身のSecure VMを持ち、Git、GitHub CLI、Node.jsなどを利用した開発が可能。

実際に既存GitHubリポジトリの改修からPR作成まで完遂した。

一方、GitHubのコメント取得やコマンド実行などで頻繁な承認が発生することが確認された。

詳細は第6章に記録する。

**判断：実装能力は確認できたが、現状の運用方式では採用を見送る。**

### 5.2 Muse＋Google Antigravity

既に契約しているGoogle AI PlusのAntigravity利用枠を活用し、Museをクラウド実行環境として利用する構成を検討した。

しかし、Google公式FAQでは、個人向けプランのAntigravityログインを第三者のコーディングエージェントから利用する方式はサポート対象外であり、利用条件違反によりアカウント停止等につながる可能性が示されている。

Google AI Plusに契約していることと、Museから利用できることは別の問題である。

Google AI StudioのAPIキーを使う方法はあるが、Google AI Plusの契約枠とは別である。

**判断：利用条件上のリスクを考慮し、MuseからGoogle AI PlusのAntigravity利用枠を使う構成は採用保留。**

公式情報：[Google Antigravity FAQ](https://antigravity.google/docs/faq)

### 5.3 Muse＋Cursor

CursorのエージェントをMuseのVMで利用する案。

別サービスの契約と、Muse側の承認操作・環境管理が必要になる可能性がある。Grok系プランの新規契約とAPI利用も候補に挙がったが、契約・接続試験には至っていない。

Muse自身にクラウドVMがある一方、Cursorにも独自の実行・連携機能が存在するため、両者を組み合わせる必要性は再評価が必要。

**判断：費用と構成の複雑さから優先度を下げる。未検証。**

### 5.4 Qwen Code / Qwen系エージェント

低コストの代替候補として検討。

Qwen Code自体はオープンソースのコーディングエージェントだが、CLIの無償利用と、クラウド上で無料・継続的に実装を実行できることは同義ではない。

モデルの開発能力や無料利用枠、クラウド上でのGitHub連携方式は未評価。

**判断：低コスト候補として保留。**

### 5.5 OpenCode Go

OpenCodeはCLI型のコーディングエージェントで、Goは月額10ドルのモデル利用プラン。

GitHub Actionsを実行基盤として利用でき、Issue・PRコメントからの起動、ブランチ作成、PR提出に対応する公式連携がある。

Goにはモデル別の利用制限が存在する。利用枠超過時に従量課金へ切り替える設定には注意が必要。

特徴：

- OpenCode自体はオープンソース。
- 複数のモデルを選択できる。
- GitHub Actionsをクラウド実行環境として利用できる。
- 権限設定によって逐次承認を減らせる可能性がある。
- GitHubイベントに基づく起動を構成できる。

懸念は、Actionsワークフロー、シークレット、実行権限などの初期構築が必要なこと。

**判断：小規模開発の有力候補。ただし契約・実証とも未実施。**

公式情報：[OpenCode Go](https://docs.opencode.ai/docs/go/) / [GitHub連携](https://dev.opencode.ai/docs/github)

### 5.6 Command Code GOAT

Command Codeは複数モデルを利用できるコーディングエージェント。

GOATは月額10ドル＋決済手数料のプランで、公式Cloud機能を利用できる。

Cloudはベータ提供中で、独立したクラウド実行環境を持つ。実装・コミット後にDraft PRを作成し、同じクラウドセッションへ追加指示することも可能。

クラウド実行は、モデル利用とは別に稼働時間分の利用枠を消費する。

特徴：

- Museを中継せずクラウド実行できる。
- Cloudでは逐次承認を省略して実行する。
- 作業後にDraft PRを作成する。
- 同じセッションで追加修正できる。
- モデル別の利用枠とクラウドセッション数の制限がある。

2026年11月1日にサービスへ登録したが、Web画面でCloud開発機能は確認できなかった。

公式資料ではCLIからCloudセッションを起動する方式が案内されている。GOAT以上のプランが必要とされており、Web上の管理画面からCodexと同じように開発を開始できることは確認できていない。

**判断：クラウド自律開発の有力候補。登録のみ実施し、GOAT契約・Cloud実行は未検証。**

公式情報：[料金](https://commandcode.ai/pricing) / [Cloud](https://commandcode.ai/docs/cloud)

## 6. Museの実証試験

### 試験概要

| 項目 | 内容 |
| --- | --- |
| 実施日 | 2026-11-01 |
| リポジトリ | `YanTKYS/editor` |
| Issue | [#34 UX-05：狭い画面での主要操作への到達性改善](https://github.com/YanTKYS/editor/issues/34) |
| PR | [#35 feat: 狭い画面で主要操作への到達性を改善](https://github.com/YanTKYS/editor/pull/35) |
| 実装担当 | Meta Muse単独 |
| レビュアー | ChatGPT |
| 結果 | 修正指摘1回を経て、コードレビュー上はマージ可能と判断 |

Issueでは実装方法を細かく指定せず、既存コードの調査、実装方針の判断、テスト、PR作成までMuse自身に委任した。

### 実装品質

Museは既存のTypeScript・CSSの構成を理解し、必要な範囲で改修した。

主な成果：

- 狭幅画面でも主要操作を利用できるよう変更。
- 既存のメニューやショートカットを活用し、新規コンポーネントの追加を避けた。
- PlaywrightによるE2Eテストを追加。
- ドキュメントと変更履歴を更新。
- コミットとPR作成を完遂し、マージせずに終了。

初回レビューでは320px幅で検索ボタンがツールバーの表示領域外に出る問題を指摘した。

Museはレビューコメントを確認し、同じPRに修正コミット `98cfca3` を追加した。

修正後は320px幅のテスト、ツールバー内部のはみ出し検査、キーボード操作の確認などが追加され、GitHub Actionsも成功した。

**コードの実装能力とレビュー指摘への対応能力は、今回の課題では良好だった。**

ただし、単一の小規模Issueでの結果であり、より複雑な開発能力を証明するものではない。

### 作業時間

GitHub上で確認できた履歴は次のとおり（日本時間）。

| イベント | 時刻 |
| --- | --- |
| Issue #34作成 | 19:07 |
| 初回PR #35作成 | 20:28 |
| ChatGPTレビュー投稿 | 20:33 |
| 修正コミット追加 | 20:52 |

Issue作成からPR作成まで約81分、レビュー投稿から修正コミットまで約19分。

ただし、実際の着手時刻や待機時間は分離できていないため、これらを純粋なエージェント実行時間とは扱わない。

利用者の体感としては、従来のCodexによる開発より長く感じられた。

### 承認操作の負担

最も大きな問題は、Museが作業中に繰り返し承認を要求したこと。

レビューコメントを読み込んで対応する一連の作業だけでも、利用者に7〜8回程度の承認操作が求められた。

このため、作業中の監視と操作が必要になり、エージェントへ仕事を任せるメリットが大きく低下した。

特にCodexでは複数の開発を並列に進めながら待てていたため、Museの承認頻度は運用上の大きな負担と感じられた。

承認制は安全性を確保するための仕組みではあるが、信頼できる作業範囲を設定し、その範囲内で自律的に進行できることが望ましい。

### 実証結果

| 項目 | 判断 |
| --- | --- |
| 既存コードの理解 | 良好 |
| 実装・テスト | 良好 |
| IssueからPR作成 | 完遂 |
| PRコメントへの修正対応 | 完遂 |
| 作業速度 | 懸念あり |
| 承認操作の少なさ | 不適合 |
| 無人での継続開発 | 現状では不向き |

**結論：Museは実装能力の面では期待できるが、現在の承認方式では小規模開発の主担当に採用しない。**

追加試験は当面実施せず、自動承認や権限設定などの改善があった場合に再検討する。

## 7. 現時点の判断

2026年11月1日時点では、現在の開発体制を維持する。

| 用途 | 方針 |
| --- | --- |
| 設計・Issue作成 | ChatGPTを継続 |
| 大規模・高難度開発 | Claude Opusを継続 |
| 小規模開発 | Codex GPT-6.1 SOLを当面継続 |
| PRレビュー | ChatGPTを継続 |
| Muse単独 | 採用見送り |
| OpenCode Go | 代替候補として保留 |
| Command Code GOAT | 代替候補として保留 |
| Qwen系 | 低コスト候補として保留 |

候補の優先順位は、現時点では実装能力のランキングではない。

Command Code GOATは公式Cloud環境を利用できる点、OpenCode GoはGitHub Actionsとの連携性が高い点で評価している。

いずれも実開発での品質・速度・承認負担を確認していないため、Codexより優れているとは判断しない。

また、追加のサブスクリプション契約を急がず、ChatGPTとCodexの共通利用枠による実際の影響を確認する。

## 8. 今後の再検討条件

次の条件のいずれかを満たした場合、開発体制を再評価する。

1. 2026年12月以降の共通利用枠によって、ChatGPTの設計・レビューまたはCodexの実装に実務上の支障が生じた場合。
2. OpenCode GoまたはCommand Code GOATのクラウド実行について、実際に利用できる環境と料金条件が明確になった場合。
3. Museで自動承認や権限制御が改善され、利用者の介入負担を十分に減らせる見込みが立った場合。
4. Qwen系などで、低コストかつ安定したクラウド開発環境を利用できることが確認された場合。

### 次回試験の原則

- 新規契約は必要性を確認してから行う。
- 最初は1リポジトリ・1Issueに限定する。
- IssueからPR作成までの自律実行を評価する。
- PRレビューへの修正対応も確認する。
- 人間の承認回数と実際の拘束時間を記録する。
- 追加料金が発生する設定は原則OFFとする。
- GitHub Appや認証情報は必要最小限のリポジトリ・権限に限定する。
- 既存のブランチ保護と、PRをマージしない運用を維持する。

**品質だけでなく、利用者が作業から離れられることを採用の必須条件とする。**
